# Router 代表人的判断，确定性约束由程序执行

2026-11-02，用户确认的设计原则。约束后续开发与方案评审；本文不改变已安装运行版或模型配置。

## Router 的责任不能退化为转发

传统流程是“人直接管理多个执行会话”；本项目把其中一部分人的工作交给 Router，形成“人 → Router → Worker”。Router 代表人在已对齐的目标与授权内理解需求、组织工作、写出更精确的约束、跟踪依赖、交叉复核、验收并加工交付。验收责任是目标，不因参考框架选择轻量路由而取消。

Claude 的三层责任保持不变：亲自完成规划/关键阅读/验收等本职；亲自完成用户点名的优化、设计或交叉核验；Worker 不足时给出具体诊断、设计与指导。它可以使用辅助执行者收集证据，但不能只把原作者的自评换个说法当作独立验收。实质写入沿用既有范围接管与写入协调。[具体边界](claude-direct-work.md)。

Worker READY 表示交付可供审查，Router ACCEPTED 表示已依据实际产物/检查作出接受决定。重要假设、接口、功能和视觉质量需要相应证据；代码通过一个状态机或两个模型意见一致，都不能替代这些判断。后续集成 Worker 可以执行合并与组合测试，接受结果仍由负责的 Router 判断。

评价指标是交付质量、遗漏/返工、人的介入和总消耗；委派比例或 Router 几乎不做事不是成功指标。我们借鉴 DeepSeek 的隔离、调度和恢复逻辑，保留这个不同的产品目标。[研究差异](deepseek-superagent-study.md)。

## 模型能力要覆盖职责，而不是按模型偷偷改变角色

当前主线是承担上述判断责任的 Router。作者的使用经验偏好 Sonnet 5.5 high、Opus 5.5 medium/high；Claude 订阅与 CC harness 的配合，是这套选择的实际条件。它是针对作者工作负载与预算的判断，不是“有订阅即可保证最优”或跨任务永久模型排名。[经验与日期](router-harness-rationale.md)。

Router模型由用户根据任务与可用能力选择；模型排名与价格不作为框架契约。

较弱模型可以适合真正的轻量分发，但那会把更多规划/验收工作留给人或另一个审查者，和当前主线是不同职责配置。不能在用户选择较弱模型后，自动丢掉验收、让 Worker 自验收，或由模型自行宣布自己变成纯路由。若当前能力不足，明确缩小任务/寻求人的判断；未来显式轻量配置先 TBD。Claude 的模型和 effort 仍由用户手动选择。

## 确定性优先：在动作边界验证，不只写提醒

下表是设计分工，不表示所有资源/工作树校验都已实现；当前覆盖与缺口另列。

| 责任 | 优先承载位置 | 仍需要判断的部分 |
| --- | --- | --- |
| Router/Worker/任务/原生回合的对应关系 | 精确 ID、所属登记、结构化参数与协议校验 | 这次需求属于哪个工作方向 |
| 并发、写入范围、资源预算、暂停与接管 | 执行前的状态机、互斥/租约、容量及路径检查 | 可否拆分、是否值得并行、需要哪些资源 |
| 续派新鲜度与恢复 | sync token、revision、幂等键、持久回执，未知结果先查证 | 新证据意味着修订目标还是继续原方案 |
| 工作树准备、集成和清理 | repo/branch/base 身份、脏状态/活跃任务检查，串行集成入口 | 接口/业务是否兼容，冲突应如何解决 |
| 验收 | 程序验证谁能接受、任务状态与证据引用的结构 | Router 亲自判断证据是否充分、是否真正满足需求 |
| 沟通、设计、优先级和提示工程 | 精简规则、skill、相关上下文与模型推理 | 用户意图、权衡、美感、解释和缺口诊断 |

规则是“可明确判定的不变量放在可信的动作/状态边界，必须理解语义的决定交给 Router”。不是把所有风格偏好、探索选择都做成硬编码开关。hooks 是接入点，不能取代协调器里必要的校验；不同调用入口仍应遵守同一组关键不变量。

Anthropic 官方说明：CLAUDE.md 不保证严格遵循；命令式 hooks 可以提供事件触发的确定性行为，而 prompt/agent hooks 用模型作判断。[记忆说明](https://code.claude.com/docs/en/memory#claude-isnt-following-my-claudemd)、[hooks 指南](https://code.claude.com/docs/en/hooks-guide)。本轮没有找到“所有指令统一只有80%遵循率”的可核对官方结论，不把用户提及的数字当作通用统计。

## 不把“有 hook”写成“已强制执行”

- command hook 执行脚本与 hook 返回 additionalContext 是两回事：后者只是注入模型可读的提醒。prompt/agent hook 本身仍有模型判断，不因为叫 hook 就变成确定性规则。
- 当前协调器已有所属、回合、sync token、队列和写入互斥等程序检查；自 Claude 复核修订起，direct 微任务租约与 takeover 走同一准入（同工作树写者、人工控制、其他 Router 的 takeover/租约），存续租约也会暂缓同树写派发并进入 sync token。角色 guard 只覆盖 Write/Edit/MultiEdit/NotebookEdit；**Bash 写入完全不检查**，也不提供同 UID 的 OS 隔离——可靠做法是让 Worker 在自己的 linked worktree 执行，主 checkout 留给 Router 与人。
- 当前 hook 的统一异常路径报告错误后返回0；这是一种兼容取舍，不能称为关键边界已默认拒绝。后续复核应区分提示/通知故障与涉及已纳管写入的未知状态，按范围确定失败策略，不能为改进 guard 阻断所有无关 Claude 工作。
- 程序能要求状态/证据字段，不能仅凭字段存在证明模型真的做了独立检查。验收质量仍要靠 Router 与可观察结果。

下一轮先复核这些界面与覆盖缺口，并行方案与工作树/资源校验按证据逐步补齐；不以“程序优先”为理由顺手重写 provider、沙箱、认证或扩大自动化范围。见 [CC 方案复核说明](architecture-review-brief.md)。
