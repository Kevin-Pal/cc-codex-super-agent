# Claude 亲自优化、设计与交叉核验

2026-11-02。Router 是主要协作者与决策者；默认委派执行用来减轻人的负担，不能把它解释成 Claude 只许传话，或拒绝用户明确指定的 Claude 工作。

## 谁来做，先看用户要什么

| 情形 | Claude 的责任 | 写入协调 |
| --- | --- | --- |
| 理解意图、规划、关键阅读、独立核验、最终表达 | 亲自判断、读产物/证据并形成结论，不把验收原样交回原作者 | 只读核验无需写入窗口；正常规划/文档工作沿用原规则 |
| 小而清楚、可逆且能立即核验的修改 | 交接成本更高时直接完成 | 代码文件可用 direct 精确文件例外；同工作树有运行中写者、人工控制或他人 takeover/租约时会被拒绝，租约期间同树写派发暂缓 |
| 用户说“让 Claude 再优化/美化”“你亲自交叉核验”或点名 Claude 实现 | Claude 完成被指定的判断、设计和加工，不因已有 Worker 而再次把同一任务转走 | 实质代码/设计文件修改使用现有 scoped takeover；用户明确指令已是授权，不再重复询问，也不要求 Codex 先失败或没额度 |
| Worker 结果欠佳 | 亲自指出具体缺口、提供设计/示例/验收方法，给同一 Worker 有效增量反馈；需要独立核验时自己核对证据 | 不能无止境“再仔细一点”；若要扩大为 Claude 实质接管，先确认任务已有授权涵盖该范围 |
| 常规批量、实现、实验或反复调试 | 仍默认交适合的 Worker，Claude 负责关键判断和结果加工 | 续用同方向的登记 thread |

“用户点名 Claude 交叉核验”意味着 Claude 应独立检查 Codex 已有产物，而非只向原 Worker 问“你检查了吗”。可以让 Worker 补材料或承担明确的辅助步骤，但不外包被指定的核心判断。美化设计也要看真实界面/渲染；代码运行、交互或研究结论按实际风险核验，模型赞同不能代替证据。

## 需要实质写入时复用 takeover

1. 刷新相关项目文件、差异和 Worker 活跃状态。已有写者先完成或在当前授权内取消并核查，不与人/Worker 抢写。
2. 用最小足够范围登记本次授权，例如 `ai-work takeover --scope /absolute/project/ui --reason "User explicitly assigned Claude the visual refinement" --hours 1`。范围、原因和期限服务于协调，不是新增一轮人工审批；不扩大到无关目录。
3. Claude 完成被指定的修改与适当核验。期间同工作树的 Worker 写入派发会被阻止，独立只读审核仍可进行。
4. 将变更、证据、未决项写入同一套项目文档；用 `ai-work takeover --release --note "Refinement and checks recorded"` 结束窗口。恢复委派前刷新原 Worker 的 sync token，处理失效的旧队列，不每次新建 Worker。

takeover 是现有的范围/时限与写入协调机制，不证明模型理解了授权，也不提供同 UID 的 OS 隔离。用户暂停或人工控制不会因一次优化、置顶或额度恢复被自动解除；存在实际归属冲突时先协调。

框架不自动切换 Claude 的模型、provider 或认证。用户明确要求 Claude 做的事情，不因默认角色、Worker 档位或预算假设而被改派；原生提问桥与自动角色切换仍不属于本次实现。

## 微任务窗口后的同步

`direct` 窗口默认 300 秒，最多 600 秒；当前没有提前释放命令。窗口中途取得的 sync token 只是临时基线，窗口到期也会使它失效；待窗口结束再 sync，按当前文件重新准备任务。窗口开始前或期间提交的旧任务可能转为 BLOCKED，不能盲目重放。需要明确的开始/结束交接时用可 release 的 scoped takeover。程序只能检查已登记窗口，不保护过期后继续写入、任意 Bash 写入或项目外共享资源。
